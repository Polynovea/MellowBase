# Polynovea CMS on AWS (CloudFormation)

`polynovea.yaml` creates a complete Polynovea CMS install in **your own** AWS account. Polynovea gets no access to it.

## What it creates

| Resource | Setting | Approx. US$/month (us-east-1, Nov 2026) |
| --- | --- | --- |
| EC2 server | `t4g.small` (2 vCPU, 2 GB, arm64), Ubuntu 24.04 LTS, IMDSv2 required, the CMS and Caddy as pinned containers | 12.26 |
| Root disk | 20 GB gp3, encrypted | 1.60 |
| Data disk | 20 GB gp3, encrypted, at `/var/lib/polynovea`; snapshotted if the stack is deleted | 1.60 |
| Elastic IP | The server's fixed public IPv4 address | 3.65 |
| RDS PostgreSQL 16 *(managed only)* | `db.t4g.micro`, single zone, 20 GB gp3 (grows to 200), encrypted, no public access, deletion protection, 7-day backups | 13.98 |
| Secrets Manager secret *(managed only)* | The database admin login | 0.40 |
| S3 bucket | Encrypted, all public access blocked, HTTPS only, versioned (deleted backups kept 14 days), kept if the stack is deleted | under 0.50 for a few GB |
| Network | A new VPC, no NAT gateway | free |
| AWS Budgets alert | Emails you at 80% of the monthly budget, and when spending is forecast to pass 100% | free (first two budgets) |
| **Total** | | **about 34 managed, about 20 on-this-server** |

Prices are estimates from AWS's on-demand list prices, before tax, with light traffic. Other regions and heavy traffic cost more; your AWS bill is what counts. They are printed in the template's description too. On-this-server sites with real traffic should use `t4g.medium` (about US$12 more).

### Security

- **One role.** The server's instance role can call `secretsmanager:GetSecretValue` on the one database secret, and list, read, write and delete objects in the one bucket. Nothing else: no managed policies, no wildcards.
- **The database is reachable from the server only.** It sits in two subnets with no internet route, has no public address, and its security group admits port 5432 from the server's security group only. The server's group opens 80 and 443 only when a domain is set (Caddy answers them), SSH only from `AdminCidr`, and lets out only HTTPS, HTTP (package mirrors) and the database.
- **IMDSv2 required, and no secret in user data.** Metadata tokens are always required. The hop limit is 2, not 1, because the release package's bridged container profile runs pgBackRest one network hop from the instance, and it needs the instance role to reach the bucket. User data is readable through the metadata service and cloud-init keeps a copy on disk, so it holds only the secret's ARN (`POLYNOVEA_DB_SECRET_REF`), the bucket's name, the region, the domain and the image digests.
- **Deletion protection.** The database has deletion protection and a final snapshot; the bucket and the data disk are kept or snapshotted when the stack is deleted.

### Why not the RDS-managed master password

The design asked for RDS to generate and manage the admin password (`ManageMasterUserPassword`). The secret RDS creates holds only `username` and `password`, and RDS doesn't let anyone add fields. The setup wizard (`lib/setup/database/createdForYou.ts`) also needs the database's `host`, and refuses a secret without one, so "Created for you" would fail on every AWS install.

So the stack owns the secret instead. Secrets Manager generates the password inside it (40 letters and digits). RDS reads it by dynamic reference (`{{resolve:secretsmanager:...}}`), and an `AWS::SecretsManager::SecretTargetAttachment` adds `host`, `port` and `engine`. That's the standard shape of "an RDS secret attached to its instance", which the wizard expects. The password is still generated by AWS and never appears in the template, the link or user data. What's lost is RDS's built-in rotation of the admin password, which the CMS doesn't need: the wizard uses the admin login once, to create its own `polynovea_owner` and `polynovea_app` roles.

## The quick-create link

Quick-create links need the template in S3. At release, upload `polynovea.yaml` to a public, versioned path, then publish:

```text
https://console.aws.amazon.com/cloudformation/home?region=us-east-1#/stacks/create/review
  ?templateURL=https%3A%2F%2F<release-bucket>.s3.amazonaws.com%2Fpolynovea%2F<version>%2Fpolynovea.yaml
  &stackName=polynovea
  &param_DatabaseMode=managed
```

(one line, no spaces). The user can edit every value in the link, so nothing trust-critical goes in it: no image digest the user can't see, and never a password.

## Launching it

1. Open the quick-create link while signed in to your AWS account, and check the region in the top-right corner.
2. Fill in **Email for the budget alert**, then choose how you'll reach the site. The template refuses to start without one of these:
   - **Your domain** (for example `cms.example.com`): the site gets HTTPS and setup is at `https://<domain>/setup`.
   - Or **Your IP address for SSH** and **EC2 key pair**: setup goes through an SSH tunnel. Find your address by searching "what is my IP", and add `/32`. You also need SSH with a domain, to read the setup code from the server's log, so setting both is best.
   - **Where the database runs**: `managed` (recommended) or `on-this-server` (cheaper).
3. Tick **I acknowledge that AWS CloudFormation might create IAM resources**. That's the server's role, shown in the template.
4. **Create stack**. It takes about 10 to 15 minutes.

From the command line, `aws cloudformation validate-template` and a change set (`create-change-set`, then review, then execute) show what will happen first.

## After launch

The stack's **Outputs** tab has `SetupAddress`, `PublicIp`, `SshTunnel`, `DatabaseSecretArn` (set on the server as `POLYNOVEA_DB_SECRET_REF`) and `BucketName`.

1. **With a domain**, point its A record at `PublicIp`. Caddy gets the certificate within a few minutes of that.
2. **First boot takes several minutes** on plain Ubuntu: it installs updates, Docker and the CMS. Progress: `sudo journalctl -u polynovea-bootstrap -f`.
3. **Find the setup code** in the CMS's log over SSH: `sudo journalctl -t polynovea | grep -i setup`.
4. **Open the wizard** at `SetupAddress`: `https://<domain>/setup`, or, without a domain, `http://localhost:3000/setup` while the `SshTunnel` command is running.
5. **Database step**: `managed` → **Created for you**. `on-this-server` → **On this server**, with **Amazon S3 bucket**; the wizard suggests the bucket.

## Removing it

1. **RDS → the database → Modify**, untick **Enable deletion protection**, **Apply immediately**.
2. **CloudFormation → the stack → Delete**. The database and data disk leave final snapshots, and the bucket is kept. Delete those yourself when you're sure; snapshots and the bucket keep costing a little until you do.

## Things that can't be verified without an AWS account

These templates were validated offline only (cfn-lint, checkov, and the unit tests in `deploy/templates.test.ts`). Nothing has been deployed. The first real launch should confirm:

- RDS accepts `EngineVersion: "16"` and picks the current 16.x minor version.
- The release package's data-disk script finds the attached EBS volume (CloudFormation attaches it just after the server starts) and the first-boot script finishes on plain Ubuntu.
- `rds.force_ssl` is on by default for PostgreSQL 16 on RDS, so TLS is required without a custom parameter group.
- Actual prices in the chosen region.

Replacing the server (for example by changing `CustomImageId` on an existing stack) re-attaches the data disk only after the old server has gone, and CloudFormation creates the new attachment first. Upgrade through the CMS's System page instead, not by changing the server image.
