# Changelog

## Unreleased

Phase 1 roles and functions sign-off: all 58 SECURITY DEFINER functions pin their search_path (checked on plain PostgreSQL and Supabase, now including the polynovea_auth schema), none names a schema polynovea_app can write, and the no-DDL test for polynovea_app now also covers replacing or altering functions, triggers, sequences, comments, schema ownership, the auth tables, database CREATE (trusted extensions) and SET ROLE to the owner.
Phase 1 wave 5: bootstrap:admin writes the master admin, workspace membership and owner role directly to PostgreSQL when the admin area is on the direct path, in one transaction. Creating the auth identity still uses Supabase Auth until the built-in auth workstream.
Phase 1 wave 5: the legacy marketing tables adapter (blog posts, live metrics, social posts, ad campaigns) on the direct path. Saving live metrics replaces them in one transaction (a failed insert used to lose every metric), and writes take only each table's editable columns.
Phase 1 wave 5: the queries API routes made directly move to the direct path (routes switch). Security: on the Supabase path the developer API's release check never denied versions from models outside a token's allowlist, and restricted tokens saw every release, because two PostgREST embeds were ambiguous and failed silently; the relationships are now named and a failed read refuses instead of allowing. The platform PATCH route no longer writes arbitrary body fields.
Phase 1 wave 5: schema deployments, backups and restores, portability, upgrades, website bindings, approval requests and component actions on the direct path, which finishes lib/infrastructure. Each deployment, backup, binding, component action and upgrade completion commits with its approval or audit event. Backups and upgrade plans now refuse another workspace's environment, and an upgrade run only records a verified backup of its own workspace.
Phase 1 wave 5: environment components, System Doctor, the operability overview and provisioning runs on the direct path. A doctor run commits with the environment's health and its audit event; a provisioning run's completion commits with the environment's status, its approval and its audit event; component re-evaluation commits as one transaction.
Phase 1 wave 5: workspace connections on the direct path. Creating a GA4 connection and linking it to analytics commit together, and a duplicate connection name is reported as a conflict without the database's constraint text.
Phase 1 wave 5: environments, credential lookups and the database and Supabase connection lookups on the direct path. A duplicate environment key is reported as a conflict without the database's constraint text, and a malformed environment id answers 404.
Phase 1 wave 4: operational plan simulation and execution on the direct path, which finishes lib/intelligence. A simulation and its plan's review status, an execution's start with its pending node runs, and an execution's completion with its proof package and operational event each commit together.
Phase 1 wave 4: autonomy policies and operational plan creation on the direct path. A plan can no longer reference another workspace's reconciliation run, policy updates are validated before they reach the database, and a plan, its nodes and edges, its drift marking and its audit event commit together.
Phase 1 wave 4: the operational world model on the direct path. A discovery's nodes, edges, observations, stale marking and the run's completion commit together, so a failed discovery leaves the previous world model intact.
Phase 1 wave 4: ML governance (retention, prediction feedback, online evaluation) and predictive plan comparison on the direct path. Retention deletes the four kinds of expired learning data in one transaction, and feedback, comparisons and scenario selection commit with their audit events.
Phase 1 wave 4: operational ML (learning policy, model registry, feature snapshots, training, predictions and outcomes) on the direct path. A model version takes its number under a lock, and the new version, the previous version's retirement, deployment and evaluations commit together.
Phase 1 wave 4: desired state and reconciliation on the direct path. A new desired-state revision takes its number under a lock, and a reconciliation's drift, resolutions, completion and audit event commit together.
Phase 1 wave 4: migration strategy runs and batches on the direct path. Run and batch updates are scoped to the workspace, a completed run commits with its audit event, and entry versions are read through the entry's workspace.
Phase 1 wave 4: data-aware change assessments on the direct path. An assessment, its operational event and its audit event commit together, and the target schema version is read through its model's workspace.
Phase 1 wave 4: deterministic remediation on the direct path. A remediation can no longer be linked to another workspace's drift item, and a run's completion, outcome event and audit event commit together.
Phase 1 wave 4 begins: intelligence discovery reads, canonical schema deployment and the operational overview's run lists on the direct path. A schema deployment, the environment's deployed-schema marker and its audit event now commit together.
Phase 1 wave 3: content analytics and GA4 sync on the direct path, which finishes lib/content. Migration 0070 makes the snapshot key treat a missing version as a value: GA4 syncs no longer add duplicate snapshots for unpublished entries on every run (existing duplicates move to content_analytics_snapshots_duplicate_archive). The GA4 connector response no longer includes its encrypted config, and a manual snapshot can only name the entry's own version.
Phase 1 wave 3: publication targets and jobs on the direct path. Dispatching a job no longer returns the target's encrypted config, a target's own headers can no longer replace the delivery's signature or idempotency headers, target config from the request is validated (HTTPS, public address, plain single-line headers), and each publication job commits with its delivery job.
Phase 1 wave 3: webhook subscriptions and deliveries on the direct path. Subscription writes commit with their audit events, each queued delivery commits with its job, and an attempt's outcome commits as one. Event filters from the request are validated, and another workspace's subscription id now reads as not found on both paths.
Phase 1 wave 3: dependency, impact and asset-usage graph reads on the direct path; every lookup is scoped by workspace and a widely used entry's or asset's blast radius is no longer cut off at 1000 relations.
Phase 1 wave 3: content health (scan, findings, remediation tasks, health profiles) on the direct path. Migration 0069 keeps remediation tasks inside their workspace: a task can no longer reference another workspace's finding, entry or asset, or be assigned to a non-member. Scans and the health overview no longer stop at 1000 rows.
Phase 1 wave 3: localization writes (locales, translation links, review, stale marking) and web-quality policy, sitemap and site audit on the direct path; the sitemap and audit no longer stop at 1000 rows, and link and review writes commit with their audit events.
- Fixed: release previews (`/preview/<token>` for a release) always came back empty on Supabase, because their lookup of entries and models was ambiguous. Preview tokens and saved entry views can run on the direct PostgreSQL path (`content=postgres`).
- Content search and saved searches can run on the direct PostgreSQL path (`content=postgres`); the saved-search filter uses bound parameters instead of a PostgREST filter string, and a malformed ID filter returns no results instead of an error.
- Editorial workflow and collaboration (assignments, comments, watchers, the editorial queue) can run on the direct PostgreSQL path (`content=postgres`). **Security:** comment mentions are limited to active workspace members on both paths (a mention notifies its recipient about the entry), and an entry's workflow is read only through the entry's workspace. Fixed: the "My work" queue never listed entry assignments on Supabase (ambiguous relationship).
- Content releases and the editorial calendar can run on the direct PostgreSQL path (`content=postgres`). The release detail and list read their items, entries, versions and history with explicit queries scoped by workspace on every table, return child lists in a fixed order, and never pass database text to the browser.
- Content preflight and destination assurance (with the web-quality policy, locale and localization-status reads they use) can run on the direct PostgreSQL path (`content=postgres`). Entry version reads now always take the workspace on both paths, so a future caller cannot skip the workspace check.
- Content entries and versions can run on the direct PostgreSQL path (`content=postgres`). Validation, uniqueness and relation rules are shared by both paths. On the direct path, every version read requires the entry's workspace, the uniqueness check sees every entry of the model (no 1000-row cap), and database errors from the entry SQL functions no longer reach the browser.
- Admin user profiles (`/api/admin/users`, `/api/admin/me`) can run on the direct PostgreSQL path (`admin=postgres`): creating or updating a member writes the profile and its default workspace membership in one transaction. `/api/admin/me` no longer returns raw database error text.
- Developer schema-delivery and import runs can run on the direct PostgreSQL path (`developer=postgres`). The developer area's audit events now follow the area's own backend switch, and import-run updates are scoped by workspace on both paths.
- Agent and extension governance can run on the direct PostgreSQL path (`developer=postgres`). On the direct path, binding an API token to an agent re-checks both under a row lock (a token revoked a moment earlier cannot be bound), and installing an extension writes the installation, every permission grant and the audit event in one transaction (the Supabase path ignored failed grant writes).
- The developer delivery API (`/api/v1/content`, `/api/v1/entries`) and the workspace export can run on the direct PostgreSQL path (`developer=postgres`). On the direct path an export includes every row; over Supabase each table stops at 1000 rows, so large workspaces got incomplete exports. Published content is now returned newest first on both paths (the Supabase path's order was undefined), and a malformed entry ID is a 404.
- Developer API tokens and API request authentication can run on the direct PostgreSQL path (`developer=postgres`). Fixed: an API token's `last_used_at` was never recorded (the update was built but never sent). Creating and revoking a token now commit with their audit events on the direct path.
- Asset upload, file replacement, the workspace upload quota and storage-connection resolution can run on the direct PostgreSQL path (`media=postgres`). On the direct path an upload writes its asset row and audit event together, a replacement reads back its history row in the same transaction, and the quota is summed in the database (the Supabase path could undercount a workspace with more than 1000 assets).
- Media collections can run on the direct PostgreSQL path (`media=postgres`): changes commit with their audit events, and asset counts are counted in the database instead of from a list capped at 1000 rows.
- The Command Center's recent jobs, findings, releases, environments and audit events have a stable order when rows share a timestamp (both data paths). Local test databases are now one stack per checkout (`node scripts/dev-db/setup.mjs`; `--down` removes it), and `npm run test:dual` refuses to start until both databases and PostgREST are on the newest migration.
- The admin activity log, the admin profile lookup behind sign-in, and the Command Center can run on the direct PostgreSQL path (`admin=postgres`). The Command Center reads each table once (10 queries instead of 26), and a failed activity-log write is now logged on the server instead of disappearing.
- Delivery jobs (the operations area) can run on the direct PostgreSQL path (`operations=postgres`). On the direct path, messages that the SQL functions raise for the caller (such as "Only terminal jobs can be replayed") reach the API caller whatever SQLSTATE they use, as they did over PostgREST, while errors from statements inside a function stay hidden.
- Database install works with a managed database's non-superuser admin (RDS master user, Azure administrator): the role step no longer names superuser-only attributes, takes temporary SET membership in the owner role for the schema owner change, sends SCRAM verifiers instead of plaintext passwords, closes temporary tables to PUBLIC, and refuses to continue if the owner or app role holds a bypass attribute. Migration `0068` fixes 0067's default privileges (new functions are not executable by PUBLIC), revokes EXECUTE from Supabase's `anon` and `authenticated` roles, and refuses member role assignments across workspaces; any such existing rows are moved to `member_roles_cross_workspace_archive`. The Supabase path's actor resolver and audit logger now report query errors instead of hiding them, and a failed audit insert no longer sends its webhook.
- **Security:** the CMS actor resolver now ignores a member's role assignment when the role belongs to another workspace (both data paths). Before, a `member_roles` row pointing at another workspace's role granted that role's permissions. The platform area (workspace lookup, actor resolver, role and collaborator lists) can run on the direct PostgreSQL path (`platform=postgres`).
- Content models (the schema area) can run on the direct PostgreSQL path (`schema=postgres`). Schema validation, diff classification and the unsafe-change gate are shared by both paths. On the direct path, database errors from creating or applying a model no longer reach the browser; the duplicate-apiKey conflict keeps its message. Model metadata updates moved from the route into the service and are scoped by workspace.
- Redirects can run on the direct PostgreSQL path (`routing=postgres`). Updates write their history row, the change and the audit event in one transaction, and bulk imports are atomic. Locale filters are bound parameters instead of a PostgREST filter string.
- Routes (the routing area's route service) can run on the direct PostgreSQL path (`routing=postgres`). Registering a route is atomic: a failed registration no longer clears the entry's canonical route. Path changes and deletions commit with their dependency edges and audit events. The single-route lookup moved from the route handler into the service.
- Navigation can run on the direct PostgreSQL path (`POLYNOVEA_DATA_BACKEND=...,navigation=postgres`). Menu creation, draft saves, publishing and deletion are atomic with their dependency edges and audit events, and concurrent draft saves get consecutive version numbers. Menu rename and delete moved from the route into the navigation service. Fixed: "where used" for navigation always returned nothing on Supabase (ambiguous relationship).
- The shared platform audit logger follows the `platform` switch in `POLYNOVEA_DATA_BACKEND`. On the direct path the audit row and its webhook deliveries are written in one transaction, and a failure is logged on the server instead of being dropped silently.
- Database provisioning no longer emulates Supabase on a plain PostgreSQL target: it stops creating the `auth.jwt()` shim, an `auth` schema and the `pgcrypto` extension (nothing uses them), and creates the compatibility role names without `BYPASSRLS`. The `postgres.pgcrypto` preflight check is gone.
- Migration `0067` adds the `polynovea_owner` and `polynovea_app` database roles: the app role gets row access through a row-level security policy on every table, executes every CMS SQL function (no longer executable by `PUBLIC`), and cannot run DDL. On a plain PostgreSQL database `db:migrate` first creates the NOLOGIN role names older migrations grant to (`anon`, `authenticated`, `service_role`, `postgres`), or says exactly what an administrator must run. Supabase installs keep every existing grant.
- **Breaking:** PostgreSQL connections now always verify TLS certificates. Set `DATABASE_CA_CERT` or `DATABASE_CA_CERT_FILE` for providers with their own CA (Supabase, AWS RDS), or `sslmode=disable` for a private network. See `docs/self-hosting/POSTGRESQL.md`.
- Extension network requests now resolve the target host and refuse any private, loopback, link-local or metadata address.
- Upgraded Next.js to 15.5.29 and zod to 4.6.6, and patched undici, sharp, source-map-js, vite, vitest and brace-expansion.
- Removed slow-regex paths in upload naming and markdown link extraction, tightened schema.org context checks, pinned AES-GCM tag length and set read-only CI token permissions.
- `DELETE /api/upload` only removes unregistered objects under the caller's own workspace prefix; registered assets are retired through the asset API. Deletions are audited.
- Outbound requests (webhooks, publication targets, connection verification, S3/R2/MinIO and Supabase Storage clients, extension network broker, delivery worker) validate destination addresses at connect time, closing the DNS-rebinding window. IPv4-mapped IPv6 and other reserved ranges are now blocked. The delivery worker previously had no destination check.
- Admin sessions resolve the profile by the immutable auth user ID. Email links a legacy profile once, only when the identity's email is confirmed. Migration `0066` makes `admin_users.auth_user_id` unique.
- **Breaking (API):** `POST /api/upload/sas` requires `size` in bytes. The size and content type are signed into the upload URL. Single files are capped at 10 MB (images) and 200 MB (video), and an optional `MEDIA_WORKSPACE_QUOTA_BYTES` caps each workspace.
- API errors no longer expose database, driver, network or provider messages; they return the route's message with a reference ID that is logged server-side.
- Schema-run history reports query failures instead of an empty list; website revalidation has a 5-second timeout and reports failures.
- The shared modal is an accessible dialog (labelled, focus-trapped, restores focus); login fields have associated labels, autocomplete and announced errors.

## 0.1.0-alpha.1 — 2026-09-21

- Removed the identity-specific master-account runtime bypass; every administrator now requires an auditable profile, workspace membership and role assignment.
- Added a server-only `bootstrap:admin` command and migration `0064` to retire the legacy client bootstrap policies safely.
- Admin create/update flows now keep default-workspace membership and system roles synchronized.
- Added a checksum-ledger-aware `db:migrate` command for fresh installs and controlled upgrades.
- Removed the bundled container runtime and its admin controls; OSS V1 now has one documented Node.js plus Supabase-compatible deployment path.
- Governed agent identity, provenance and constrained extension foundations.
- Governed MCP transport package.
- Supabase browser configuration now fails explicitly when absent; it no longer contains a Polynovea project fallback.
- Delivery Operations UI now lists every worker job kind, and publication delivery resolves its configured signing secret correctly.
- Expanded README, self-hosting, contribution and security documentation; direct generic PostgreSQL runtime support is explicitly deferred.
- CI/release gates now include the production build, SDK build, CLI smoke test and `git diff --check` in addition to type-check, lint, tests, audit and secret scanning.
- Added `npm run certify:live` and recorded a clean managed-Supabase install, owner bootstrap, authenticated Phases 8–13, worker execution, production restart and idempotent migration reconciliation.
- Added the idempotent `npm run seed:starter` onboarding command for a first Article model and welcome draft.
